# Центральный оркестратор Kripto Guru — MVP

## Что делает эта версия

Workflow `.github/workflows/kripto-guru-orchestrator.yml`:
- запускается вручную или по расписанию раз в 2 часа;
- ищет одну открытую GitHub Issue с меткой `agent-ready`;
- обрабатывает не более одной задачи за запуск;
- назначает команду A/B/C по номеру Issue (детерминированное распределение) и вызывает Gemini с fallback-моделью, чтобы назначить одну из ролей ARCHITECT / FRONTEND / BACKEND / QA / SECURITY / ANALYST;
- при статусе READY запускает reusable workflow `role-worker.yml`;
- BACKEND ограничен `src/index.ts`, `src/api.ts`, `src/service.ts`, `src/state.ts`, `src/tenants.ts`; FRONTEND — `miniapp/web/*`. Оба могут предложить diff только в существующих файлах (до 3 файлов / 250 строк); остальные роли пока формируют handoff-отчёт без изменения исходников;
- выполняет `npm ci`, `npm run typecheck`, `npm test` и вторую AI-проверку diff (не заменяет независимый human review); при ошибках или REJECT PR не публикуется;
- публикует пакет диспетчера и результат исполнителя отдельными Draft PR;
- оставляет ссылки в Issue; неполные задачи помечает `agent-blocked`.

Ограничитель частоты: максимум одна Issue за запуск; расписание — 12 запусков в сутки. При пустой очереди LLM не вызывается. На ошибках временного характера допускается ограниченный retry и fallback на вторую модель.

## Что эта версия НЕ делает

- Роли ARCHITECT, QA, SECURITY и ANALYST не изменяют прикладной код; BACKEND/FRONTEND ограничены разрешёнными файлами и лимитами diff.
- Не исправляет замечания QA автоматически и не повторяет цикл исправлений.
- Вторая AI-проверка не является независимым аудитом; PASS не доказывает отсутствие дефектов. Human code review обязателен.
- Не сливает PR, не деплоит и не включает LIVE.
- GitHub Actions остаётся событийным исполнителем, а не постоянно работающим сервером.

Это ограниченный автоматический цикл «Issue → диспетчер → один исполнитель → runtime checks → AI review → Draft PR». Это ещё не завершённая автономная команда: нет автоматического исправления замечаний, полноценной межагентной передачи и независимого human review.

## Как поставить задачу

Создать GitHub Issue и добавить метку `agent-ready`. В описании обязательно указать:
1. Цель и причину.
2. Контекст и связанные файлы/PR.
3. Разрешённую область изменений.
4. Что запрещено менять.
5. Проверяемые критерии приёмки.
6. Команды проверок и требуемые доказательства.

Если данных недостаточно, диспетчер должен пометить пакет BLOCKED, а не придумывать требования. Workflow автоматически создаёт метки `agent-ready`, `agent-dispatched` и `agent-blocked`; секреты `GEMINI_API_KEY` (команда A), `GEMINI_API_KEY_TEAM_B` и `GEMINI_API_KEY_TEAM_C` должны быть доступны GitHub Actions. Команда выбирается по `Issue number mod 3`; диспетчер и исполнитель одной задачи используют один и тот же выбранный ключ. Это распределяет запросы между тремя проектами, но не гарантирует суммирование квот и не обходит ограничения Google. Для расписания и ручного запуска workflow должен быть слит в default branch; до этого PR не исполняет центральный цикл.

## Безопасность

- Никаких платных API или подписок.
- Секреты только в GitHub Actions Secrets.
- Все результаты — отдельные ветки и Draft PR.
- Человеческое утверждение обязательно.
- Реальные сделки, LIVE, production deploy и merge запрещены.
