# Протокол работы команды

## Жизненный цикл задачи

1. **Backlog** — задача записана, но ещё не взята.
2. **Ready** — есть владелец, контекст, критерии приёмки и ограничения.
3. **In progress** — работа идёт в отдельной ветке.
4. **Review** — открыт PR, приложены результаты проверок.
5. **Blocked** — указана конкретная причина блокировки и необходимое решение.
6. **Done** — критерии приёмки выполнены, review завершён; merge/deploy учитываются отдельно.

## Обязательный шаблон задачи

- Цель и причина.
- Контекст и связанные файлы/PR.
- Область изменений.
- Что запрещено менять.
- Критерии приёмки.
- Команды тестирования и ожидаемые доказательства.
- Риски и план отката, если применимо.

## Обязательный отчёт исполнителя

- Статус: DONE / PARTIAL / BLOCKED.
- Что изменено (точные пути).
- Ветка, commit SHA и PR URL.
- Какие проверки запускались.
- Результат каждой проверки: PASS / FAIL / NOT RUN.
- Что не проверено и почему.
- Оставшиеся риски и следующий шаг.

## Работа с Git

- Работать только в отдельной feature/fix/team ветке.
- Не коммитить напрямую в main.
- Не переписывать чужие ветки и не force-push без отдельного разрешения.
- Не сливать PR и не публиковать production без явного разрешения CEO.
- Не менять secrets, Telegram settings, Cloudflare production config и deploy workflow без согласования.

## Доказательства качества

- Успешный CI не заменяет проверку в реальном Telegram iOS WebView.
- Playwright screenshot — предварительная визуальная проверка, а не подтверждение поведения на реальном устройстве.
- Не заявлять, что дефект устранён, пока не показан воспроизводимый тест или иное надёжное подтверждение.
- При недоступном тесте честно писать NOT RUN.

## Координация нескольких ИИ-сеансов

GitHub PR/Issue — общая асинхронная почта. Каждый сеанс перед работой читает актуальную задачу и последние комментарии, затем публикует отчёт. Этот механизм не запускает и не будит закрытые чаты автоматически.
