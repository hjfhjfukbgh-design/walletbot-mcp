# Отчёт об анализе задачи Issue #700 (SECURITY)

## 1. Threat Model & Risk Analysis (Модель угроз и риски)

* **Границы доверия (Trust Boundaries):**
  * **Клиентский слой / Telegram Mini App:** Недоверенная среда выполнения. Доступ к API защищён заголовком `X-Api-Key` (`src/api.ts:L26`) или подписью `Telegram.WebApp.initData` (`src/api.ts:L35-L38`). Поля ввода (маржи, цены, режимы) проходят строгую серверную валидацию.
  * **Вендор Walt MCP:** Внешний провайдер ликвидности и исполнения ордеров. Связь защищена через OAuth 2.1 с PKCE (`src/oauth.ts`) и Streamable HTTP MCP-клиент (`src/mcp.ts`).
  * **Хранилище (Cloudflare KV / SQLite):** Изоляция данных пользователей обеспечивается префиксами тенантов (`src/tenants.ts`), предотвращая перекрёстный доступ к ключам и позициям.
* **Секреты и авторизация:**
  * Учётные данные OAuth, токены доступа и `API_SECRET` хранятся исключительно в безопасном серверном контексте Cloudflare Workers / KV. В публичном коде и клиентской части секреты отсутствуют.
* **Деньги и риск-лимиты:**
  * Торговые операции в режиме `LIVE` жестко заблокированы на уровне бэкенда (`src/bot.ts:L81-L87`, `src/service.ts:L105-L107`).
  * Срабатывают серверные ограничения: максимальный процент капитала на сделку (`MAX_ORDER_PCT = 25`, `src/env.ts:L48`), дневной лимит убытка (`MAX_DAILY_LOSS_PCT = 5`, `src/env.ts:L50`), whitelist активов (`ALLOWED_MARKETS`, `src/risk.ts`).
* **LIVE-переключатели:**
  * По умолчанию система работает в безопасном режиме `DEMO / paper` (`src/state.ts:L43`). Переход в `LIVE` требует явного подтверждения (`/live CONFIRMO`, `src/commands.ts:L58`), но программно заблокирован до полного прохождения аудита контрактов закрытия и верификации вендора.

## 4. Риски и пробелы

1. **Отсутствие закрывающих контрактов LIVE:** Метод `closePosition` в `src/walt.ts:L90-L93` намеренно выбрасывает `WaltError`, блокируя реальное закрытие позиций в LIVE-режиме.
2. **Эвристический парсинг балансов:** Функция `usdcBalance` (`src/walt.ts:L164-L183`) полагается на эвристический поиск ключей в произвольном JSON-ответе вендора, что создает риск рассинхронизации при изменении API Walt.
3. **Отсутствие интеграционных тестов с реальным API:** Все тесты и проверки проводятся изолированно без отправки реальных запросов (согласно строгим требованиям безопасности проекта).
