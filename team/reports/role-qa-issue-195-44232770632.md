## Что проверить
1. Telegram initData: отклонение отсутствующего, испорченного и просроченного auth.
2. Tenant isolation: пользователь A не может читать/удалять историю пользователя B.
3. API: список, чтение, отправка, удаление; некорректный conversationId; пустое и слишком длинное сообщение.
4. Лимиты, таймауты, обработка отказа Gemini и отсутствие утечки ключа в клиент.
5. UI: ошибки сети, повтор отправки, пустой чат, история и новый чат.
6. Отдельно подтвердить, что Companion не имеет доступа к торговым методам и не может отправлять ордера.
7. Проверить актуальный preview smoke run и отметить любые расхождения.

### Анализ задачи Issue #195

#### 1. Вердикт
**ПРИНЯТО С ЗАМЕЧАНИЯМИ / УЛУЧШЕНИЯМИ (С ОГРАНИЧЕНИЯМИ)**. 
Текущая кодовая база содержит корректное разделение демо-режима (`paper`) и реального режима (`live`), блокировку автоматического и несанкционированного исполнения ордеров в реальном контуре, а также изоляцию пользователей (`tenants`). Однако в клиентской и серверной частях мини-приложения требуется строгая валидация входящих данных от Telegram WebApp и защита от подделки параметров ордеров.

---

#### 2. Доказательства с точными путями и символами
* **Изоляция и авторизация по TMA (Telegram Mini App):**
  * Файл `src/api.ts` (строки 21–32): авторизация проверяется через заголовок `Authorization: tma <initData>` с вызовом `validateTelegramInitData`.
  * Файл `miniapp/web/kripto-guru-api.js` (строки 42–59): извлечение и ожидание `initData` через `window.Telegram?.WebApp?.initData`.
* **Защита LIVE-режима:**
  * Файл `src/bot.ts` (строки 42–47): жесткая блокировка `live`:
    ```ts
    if (live) {
      state.running = false;
      state.paused = "LIVE временно заблокирован до включения подтверждения каждой сделки и проверки лимитов риска";
      msgs.push(`⏸️ ${state.paused}`);
      return;
    }
    ```
  * Файл `src/service.ts` (строки 118–127): метод `setMode` возвращает отказ при попытке переключения в `live`:
    ```ts
    if (target === "live") {
      return "LIVE пока закрыт: сначала подключаем подтверждение каждой сделки, сверку открытых позиций и жёсткие лимиты риска. ДЕМО работает полностью без кошелька.";
    }
    ```
* **Валидация на стороне сервера:**
  * Файл `src/manual.ts` (строки 43–75): проверка маржи, плеча, объема, лимитов риска и допустимых диапазонов цен (`takeProfit`, `stopLoss`) перед открытием ручной сделки.

---

#### 3. Риски и пробелы
1. **Недоверенные данные от клиента:** Клиентские скрипты (`miniapp/web/kripto-guru-ui.js`, `miniapp/web/trading-v2.js`) передают параметры маржи, плеча и символов; сервер (`src/api.ts`, `src/manual.ts`) должен полностью пересчитывать и верифицировать их, не доверяя расчётам интерфейса.
2. **Обработка сетевых ошибок и таймаутов:** При обрыве соединения с публичными котировками (`publicMid` в `src/prices.ts`) интерфейс может отображать устаревшие кэшированные данные, если нет явного индикатора состояния связи (stale/offline).
3. **Ограничения бюджета и окружения:** Бюджет 0, LIVE-сделки и реальный исполняемый трейдинг **запрещены** (разрешен только режим DEMO и read-only интеграции).

---

#### 4. Один следующий шаг
Провести аудит эндпоинтов `POST /api/demo/open` и `POST /api/manual` на предмет исчерпывающей серверной валидации всех числовых параметров (leverage, marginUsd, takeProfit, stopLoss) с использованием целочисленной арифметики (в микро/миллиделениях), исключая инжекцию некорректных типов.

* [ ] Запрос с невалидным или отсутствующим заголовком `Authorization: tma ...` отклоняется сервером с кодом `401 Unauthorized`.

* [ ] Клиентский интерфейс корректно обрабатывает ошибки API без падений и бесконечных циклов рендеринга.
