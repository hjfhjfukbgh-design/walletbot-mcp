### Вердикт
Архитектура проекта представляет собой гибридную систему: Telegram Mini App (Serverless) + Cloudflare Worker (Trading Engine). Текущая реализация содержит критический риск: логика исполнения ордеров и управления состоянием распределена между `src/bot.ts` (legacy) и `src/trading/engine.ts` (новый движок). Отсутствие единого источника истины для состояний позиций в DEMO-режиме может привести к рассинхронизации баланса и некорректным расчётам PnL.

### Доказательства
1. **Дублирование логики:** В `src/bot.ts` (функция `tick`) реализована логика управления позициями через `state.grid.position`, в то время как `src/trading/engine.ts` (Durable Object) содержит собственную SQL-схему для позиций (`positions` table).
2. **Риск рассинхронизации:** `src/api.ts` обращается к обоим источникам (`stateView` для legacy и `engineRequest` для DEMO), что создает состояние гонки при обновлении баланса.
3. **Пути:**
   - `src/bot.ts`: Legacy-логика тиков.
   - `src/trading/engine.ts`: Новый движок на базе Durable Objects.
   - `src/state.ts`: KV-хранилище, которое используется как глобальное состояние, что не является атомарным при конкурентных запросах.

### Риски и пробелы
- **Отсутствие атомарности:** Использование KV (`src/state.ts`) для хранения состояния сетки не гарантирует консистентность при одновременном вызове `tick` (cron) и `handleApi` (Mini App).
- **Безопасность:** В `src/api.ts` есть попытка записи в KV `tenant:user:` без проверки на ошибки записи, что может привести к частичному отказу в обслуживании (DoS) для конкретного пользователя.
- **Пробел:** Отсутствует единый реестр транзакций (Ledger), который бы связывал изменения баланса в `paper` (KV) и `engine` (SQL).

### Один следующий шаг
**Рефакторинг контракта состояния:** Перенести ответственность за хранение всех активных позиций (как сетки, так и ручных) из KV (`bot:state`) в Durable Object `TradingEngine`. Это обеспечит атомарность операций и единый источник истины для PnL и баланса.

### Критерии приёмки
1. `src/bot.ts` перестаёт напрямую модифицировать `state.paper.cash` в KV.
2. Все операции с балансом и позициями проходят через `TradingEngine` (Durable Object).
3. `src/state.ts` используется только для конфигурации сетки, а не для учёта финансовых показателей.
4. Проведены тесты (typecheck + vitest) на корректность вызова методов `TradingEngine` из `bot.ts`.

### Что не проверено
- Фактическая работа Durable Objects в условиях высокой нагрузки (не запускались runtime-тесты).
- Корректность миграции существующих данных из KV в SQL-таблицы `TradingEngine` (требуется отдельный скрипт миграции).
- Влияние задержек (latency) при обращении к Durable Object из Worker-контекста на скорость исполнения тиков.
