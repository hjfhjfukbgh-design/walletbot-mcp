### 1. Архитектурный вердикт
Проект `walletbot-mcp` представляет собой гибридную serverless-систему: интерфейсная часть (Telegram Mini App) хостится на Telegram Serverless (`tgcloud`), а торговая логика, cron-триггеры и интеграция с Walt MCP выполнены в виде Cloudflare Worker (`src/index.ts`, `src/api.ts`). Управление состоянием распределено между Durable Objects (`TradingEngine`), Cloudflare KV (`STATE`) и изоляцией на уровне пользователей (`src/tenants.ts`).

Сильные стороны текущей архитектуры:
- Использование strict fixed-point arithmetic (`src/trading/money.ts`) исключает плавающие ошибки округления в расчете маржи, комиссий и PnL.
- Разделение на DEMO-симулятор и реальный Walt MCP защищает пользователя от случайных потерь при незавершенной настройке.
- Реализованы жесткие risk limits (`src/risk.ts`, `src/env.ts`, `wrangler.toml`), включая лимит плеча (≤3x), дневного убытка (5%) и маржи по ордеру (25%).

Критичные архитектурные уязвимости и риски:
- Хранение ключей авторизации через ручной `/link <API_SECRET>` и хрупкий эвристический поиск balances в `src/walt.ts` создают точки отказа при изменении внешнего ответа Walt MCP.
- Отсутствие единого атомарного task queue на уровне Workers для обработки параллельных cron и webhook-запросов (используется параллельный `Promise.all` по tenants, что при росте базы пользователей упрется в лимиты KV/Workers CPU).

### 2. Схема компонентов и поток задачи

```
[ Telegram User ]
       │
       ▼ (Webhook / Command)
 [ Telegram Serverless / Worker /telegram ]
       │
       ▼
 [ Cloudflare Worker Router (`src/index.ts`) ]
       ├──▶ [ /api/* ] ──▶ [ Mini App / API Handler (`src/api.ts`) ]
       │                       │
       │                       └──▶ [ TradingEngine (Durable Object) / KV ]
       │
       └──▶ [ Cron / Scheduled */5 min ]
               │
               ▼
       [ Tenant Tick Engine (`src/tenants.ts`, `src/bot.ts`) ]
               │
               ├──▶ (DEMO) Engine Matcher / Trigger Check
               └──▶ (LIVE) Walt MCP `perps_prepare_*` ──▶ `perps_execute_operation`
```

**Поток стандартной задачи (на примере тика сетки):**
1. Cloudflare Cron (`triggers.crons = ["*/5 * * * *"]`) вызывает `scheduled()`.
2. `listTenantIds()` собирает активных пользователей из KV.
3. `handleTenantTick()` запускает изолированный `tenantEnv` для каждого пользователя.
4. `tick()` выполняет проверку котировок, срабатывание TP/SL и риск-контроль.
5. Результат отправляется пользователю в личный чат через `telegram.ts`.

### 4. Текущие подтвержденные возможности и пробелы

**Подтверждено в коде:**
- `package.json`: зависимости зафиксированы, `undici` пропатчен через `overrides`, скрипты `test` и `typecheck` настроены.
- `src/trading/money.ts`: строгая fixed-point арифметика с масштабами `MONEY_SCALE` (10^6) и `PRICE_SCALE` (10^8).
- `src/risk.ts`: жесткие проверки лимитов (`maxLeverage`, `maxDailyLossPct`, `maxOrderPct`).
- `src/walt.ts`: двухэтапный паттерн Walt MCP (`perps_prepare_*` -> `perps_execute_operation`) с защитой от повторного выполнения.

**Пробелы и гипотезы:**
- *(Гипотеза)* Поведение Mini App внутри реального Telegram iOS WebView при нестабильном интернет-соединении (не подтверждено тестами на реальных устройствах).
- *(Пробел)* Отсутствие единого персистентного task queue (все задачи выполняются немедленно в рантайме Worker/DO, что уязвимо при сбоях сети во время внешних вызовов).
- *(Пробел)* Отсутствие автоматических интеграционных тестов для взаимодействия с реальным/мокированным Walt MCP API (тесты покрывают изолированные модули, но не полный жизненный цикл ордера).

### 5. Риски и меры

1. **Риск несанкционированной LIVE-торговли**
   - *Мандат:* LIVE жестко заблокирован в коде и конфигурации (`src/service.ts`, `src/trading/engine.ts`). Любые попытки переключить режим без явного прохождения защитных проверок отклоняются с ошибкой.
2. **Риск исчерпания лимитов KV / Cloudflare CPU**
   - *Мандат:* Ограничение частоты cron (каждые 5 минут), минимизация записи в KV (1 запись на состояние тика), использование Durable Objects для изоляции состояния.
3. **Риск утечки секретов через репозиторий**
   - *Мандат:* Использование GitHub Actions Secrets исключительно для CI/CD и wrangler; запрет на жесткое кодирование токенов и ключей в исходном коде.
