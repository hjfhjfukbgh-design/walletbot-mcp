### 3. Ошибки / галлюцинации / пробелы в отчёте

1. **Галлюцинация о тестах:** В отчёте утверждается: *«На данный момент основное покрытие тестами сосредоточено на чистых функциях математики и позиций (`money.ts`, `positions.ts`)...»*. В предоставленных файлах репозитория **отсутствуют** какие-либо тесты (нет файлов `*.test.ts`).
2. **Преувеличение степени готовности мультитенантности:** Отчёт презентует мульти-арендность как полностью протестированную и изолированную реальность, хотя `src/tenants.ts` переопределяет `KVNamespace` через префиксы ключей, а `TradingEngine` (DO) принимает запросы без строгой проверки того, что запрашивающий `userId` совпадает с контекстом DO (на уровне эндпоинтов `/api/demo/*` параметры `userId` передаются из Mini App).

### 4. Риски безопасности

1. **Доверие к `userId` от клиента:** В `src/api.ts` параметр `telegramUserId` извлекается из заголовка `tma <initData>` (или передается в запросах эмулятора/демо). Валидация подписи `initData` через `validateTelegramInitData` упоминается в коде `src/api.ts`, однако в предоставленном листинге `src/api.ts` функция `validateTelegramInitData` оборвана (код обрывается на `pnlMicro(...)`), что не позволяет проверить криптографическую корректность валидации Telegram WebApp Data.
2. **Изоляция в Durable Object:** `TradingEngine` обслуживает запросы, принимая `userId` из параметров URL (например, `/history?userId=...` или тело запроса). Если проверка подлинности на уровне API будет скомпрометирована, один пользователь потенциально сможет запросить данные другого черезпрямые вызовы к DO.

### 6. Тест-кейсы и критерии приёмки

#### Тест-кейс 1: Проверка математики фиксированной точки (`money.test.ts`)
* **Цель:** Убедиться в отсутствии погрешностей округления при расчете ноционала и PnL.
* **Входные данные:** `qtyUnits = 100_000_000n` (1.0), `entryPrice = 50_000_000_000_000n` ($50,000), `exitPrice = 51_000_000_000_000n` ($51,000), `side = "long"`.
* **Ожидаемый результат:** `pnlMicro` возвращает корректное значение `1_000_000_000n` ($1,000.00) с учетом масштабов без использования `number` с плавающей запятой.

#### Тест-кейс 2: Проверка риск-лимитов на открытие позиции (`risk.test.ts`)
* **Цель:** Убедиться, что `checkOpen` блокирует сделки при превышении `maxOrderPct` или `maxDailyLossPct`.
* **Входные данные:** `equityUsd = 100`, `maxOrderPct = 25`, попытка открыть сделку с маржой `26` USD.
* **Ожидаемый результат:** Возвращается `{ ok: false, reason: "..." }`.

#### Критерии приёмки:
1. Команда `npm test` выполняет созданные тесты и завершается с кодом `0`.
2. Команда `npm run typecheck` не выдает ошибок компиляции TypeScript.
