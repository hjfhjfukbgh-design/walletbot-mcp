### 1. Краткий вывод
Архитектура проекта построена по гибридной серверной модели: бэкенд на **Cloudflare Workers** (TypeScript, модульная архитектура ES modules) управляет торговыми логиками, состоянием в **Cloudflare KV**, а также выполняет роль API для Telegram Mini App (`miniapp/web`) и координирует торговые операции. Для изолированного хранения демо-счетов и позиций используется встроенная база данных **SQLite** в рамках Durable Objects (`TradingEngine`). В репозитории реализованы строгие защитные механизмы: торговый режим `live` заблокирован заглушкой в коде, ключевой функционал покрыт расчетами в фиксированной точке (`src/trading/money.ts`), а риски жестко ограничены конфигурацией в `wrangler.toml` и валидаторами (`src/risk.ts`).

### 2. Текущее устройство backend с точными путями/символами

*   **Точка входа Worker (`src/index.ts`):** 
    *   Экспортирует обработчик `fetch` для маршрутизации вебхуков Telegram (`POST /telegram`), API-запросов Mini App (`/api/*`), OAuth-колбэков (`/oauth/callback`), настройки бота (`/setup`) и отдачи схем инструментов (`/tools.json`).
    *   Экспортирует обработчик `scheduled` для cron-триггеров (каждые 5 минут по расписанию `*/5 * * * *`), запускающий периодический опрос (`tick`) и мониторинг сделок.
    *   Экспортирует Durable Object класс `TradingEngine`.
*   **API-маршрутизация и обработчики (`src/api.ts`):**
    *   Функция `handleApi(req, env, ctx)` проверяет заголовок `X-Api-Key` или валидирует заголовок `Authorization: tma ...` через `validateTelegramInitData`.
    *   Поддерживает роуты DEMO-торговли (`GET demo`, `POST demo/preview`, `POST demo/open`, `POST demo/close`), состояния (`GET state`), контрактов (`GET contracts`), графиков (`GET chart`), ручных сделок (`POST manual`) и управления сеткой (`POST grid`, `POST control`).
*   **Движок торгов и позиций (`src/trading/engine.ts`, `src/trading/positions.ts`, `src/trading/money.ts`):**
    *   `TradingEngine` (Durable Object) управляет таблицами `accounts`, `positions`, `ledger` и `engine_meta` в SQLite.
    *   `src/trading/money.ts` реализует арифметику в фиксированной точке (`MONEY_SCALE = 1_000_000n`, `PRICE_SCALE = 100_000_000n`) для предотвращения ошибок округления с плавающей запятой.
    *   `src/trading/positions.ts` содержит чистые функции расчёта маржи, проскальзывания (`applyAdverseSlippage`, `applyEntrySlippage`), расчёта нереализованного PnL (`unrealizedPnl`), проверки триггеров (`checkTrigger` для SL/TP/ликвидации) и закрытия позиций (`closePosition`).
*   **Управление состоянием и конфигурация (`src/env.ts`, `src/state.ts`, `src/service.ts`):**
    *   `src/env.ts` описывает интерфейс `Env` и функцию `riskLimits(env)` для извлечения лимитов риска из переменных окружения/`wrangler.toml`.
    *   `src/state.ts` управляет чтением и сохранением структуры `BotState` в Cloudflare KV (`bot:state`).
    *   `src/service.ts` реализует бизнес-логику управления сеткой (`configureGrid`, `runGrid`, `stopGrid`, `resumeGrid`, `setMode`).
*   **Конфигурация инфраструктуры (`wrangler.toml`):**
    *   Определяет привязки Durable Objects (`ENGINE`), KV-населенные пункты (`STATE`), статические ассисты (`ASSETS`), cron-триггеры и параметры риск-менеджмента (`MAX_LEVERAGE = "3"`, `MAX_ORDER_PCT = "25"`, `MAX_DAILY_LOSS_PCT = "5"` и др.).

### 3. Один приоритетный следующий шаг и почему

**Приоритетный шаг:** Реализовать и запустить комплексное юнит-тестирование для финансовых расчетов в фиксированной точке (`src/trading/money.ts` и `src/trading/positions.ts`) через существующий фреймворк `vitest`.

**Почему это критически важно:** 
Бэкенд оперирует финансовыми расчетами (маржа, комиссии, проскальзывания, PnL) с использованием BigInt. Любая регрессия или ошибка в логике округления (`divRound`) может привести к некорректному списанию средств с демо-баланса или неверному срабатыванию стоп-лоссов/тейк-профитов. Поскольку инфраструктура тестов уже прописана в `package.json` (`"test": "vitest run"`), расширение покрытия для критического ядра `src/trading/` гарантирует математическую стабильность бэкенда до добавления новых продуктовых фич.

### 7. Риски / безопасность

*   **Финансовые риски (DEMO / LIVE):** Необходим постоянный контроль за тем, чтобы код взаимодействия с реальными контрактами Walt MCP был изолирован или заблокирован до завершения полного цикла аудита безопасности.
